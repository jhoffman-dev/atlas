# Atlas local API, v1

Atlas answers HTTP on `127.0.0.1` while it is running and the API is turned on
in **Settings → Connections**. The types are in
`packages/application/src/api/contract.ts`; why it is shaped this way is
ADR-0016.

## Connecting

Settings shows the port and the token, and writes both to the connection file:

```
~/Library/Application Support/<bundle id>/api.json
{ "port": 27183, "token": "…64 hex…", "version": 1, "enabled": true }
```

The file is owner-only (mode 0600). `enabled: false` means the API is off and
nothing is listening; `port` is 0 until it has been on once. Read the file
again when a request is refused `401`: the token changes when it is rotated in
Settings, when the file was found readable by other users, and when the
recorded port was taken at launch (Atlas then listens on another port too).
Connect to `127.0.0.1` literally, never `localhost`.

Every request carries the token:

```sh
curl -H "Authorization: Bearer $TOKEN" http://127.0.0.1:$PORT/v1/status
```

Refused before Atlas looks at it: no or wrong token (`401 unauthorized`), a
browser `Origin`, a foreign `Host` or a request target that names a host, as in
`GET http://127.0.0.1:27183/v1/status` (`403 forbidden` — send the path only),
a body over 1 MiB (`413 too_large`). No answer in 30 s is `504 timeout`, which
is not a refusal: a write may already have landed, so read the note before
retrying. The host checks in that order — target and `Host`, then `Origin`, then the token,
then the size — so a browser page learns nothing about the token. A path
outside `/v1`, or a method other than `GET`/`POST`/`PUT`/`PATCH`/`DELETE`, is
`404 not_found_route`; a query that does not decode to UTF-8, or a body that
is not JSON, is `400 invalid`. When the app has no window to answer, the reply
is `500 internal` at once, and so it is while Atlas is starting or its window
is reloading, with the message "Atlas is still starting — try again in a
moment": retry after a short pause. Every one of these refusals carries
`Connection: close` and the connection is closed after it: a pipelined request
behind a refused one is never answered, so reconnect to try again. A refusal
sent before the body was read is still delivered whole: the server reads and
discards up to 64 KiB of the unread body, for up to a second, before closing.

At most 32 connections are open at a time; more wait until one closes. A
connection takes no new request after 60 s (one in flight still finishes), so
a keep-alive client should expect to reconnect.

## Errors

```json
{ "error": { "code": "conflict", "message": "Tasks/Call Sam.md changed since you read it" } }
```

Branch on `code`, never on `message`. Codes and statuses: `invalid` 400,
`unauthorized` 401, `forbidden` 403, `not_found` / `not_found_route` 404,
`conflict` / `unsaved_in_app` / `exists` 409, `too_large` 413, `query_failed`
422, `internal` 500, `no_vault` 503, `timeout` 504. A `conflict` that time
will clear carries `retryAfter`, in seconds, beside `code` and `message`; an
Atlas query that does not read carries `at`, where in its text (see Atlas
queries).

## Paths

A note is named by its vault-relative path, with `.md`, percent-encoded as a
single segment: `Tasks/Call Sam.md` is `/v1/notes/Tasks%2FCall%20Sam.md`. Paths
that climb out of the vault, are absolute, or point into `.atlas` are `invalid`.
A path finds its note whatever its case or Unicode normalization, as the Mac's
disk does, and answers carry the note's path as the vault spells it. So do a
view's path in `/v1/views/{path}/run` and the `folder` of `POST /v1/notes`:
`folder: "tasks"` makes the note in the vault's `Tasks/`, and the answer says
`Tasks/…`.

`POST /v1/notes` creates only in a folder that already exists; a missing
`folder` is `404 not_found`, naming it. With no `name` the note is `Untitled`,
numbered past any taken — even one taken while the note was being made, so
several made at once each get their own number. If every number it tries is
taken meanwhile (it gives up after 20), it is `409 conflict`, and retrying is
safe.

A request is for the vault open when it arrived. If another vault is opened
before it finishes, it is `503 no_vault` — including after a create or a write
has landed, when reading the note back would read the other vault.

## Writing safely

Every note carries `modified`. Pass it back as `ifModified` and the write is
refused with `conflict` if the note changed in between.

- `PATCH .../properties` and `POST .../append` take it optionally.
- `PUT .../body` requires it — there is no blind overwrite.
- A note open in Atlas **with unsaved edits** refuses body writes with
  `unsaved_in_app`. Property writes go through the open pane, as a board drag
  does, so they never clobber it. One sent while that pane is still opening the
  note is `conflict` with nothing written; retrying is safe.

Rows are `{ columns, rows, truncated, sql }`. `truncated` is true when more rows
matched than came back: for a query or a view, its `limit` or the host's row cap
cut it short; for SQL, the row cap (5000 rows). A query or view never lists
notes in `.atlas` or a hidden folder, and a page is filled to its `limit` when
enough notes match.

`/v1/sql` reads the index: `files(path, title, summary, modified, size)`,
`props(path, key, idx, value_text, value_num, value_date, value_json)`,
`links(src, dst, target, kind)`, the FTS5 table `fts(path, title, body)`, and a
view `v_<type>` per type. `sqlite_master` has the exact definitions.

`/v1/capture` makes the task in `Inbox/` — made if the vault has none — as the
app's capture does, numbered if the name is taken (P30-01). In a vault whose
Task type has the `inbox` status, the task starts there: `status: inbox`,
whatever the Task template says (P30-02).

### Tasks follow GTD (P30-02)

A task's `status` is one of eight, in this order: `inbox`, `backlog`,
`next-action`, `in-progress`, `waiting`, `someday`, `longterm`, `archive`
(ADR-0029). Every write that changes or makes a task — `PATCH .../properties`,
a card moved with `POST /v1/views/{path}/move`, `POST /v1/notes`,
`POST /v1/views/{path}/notes`, `POST /v1/quick-add`, `POST /v1/capture` — is
held to the app's rules, judged on the note the request leaves (a `type`
changed in the same request counts):

- `waiting` needs `waiting_on`, a link to a Person, set before or in the same
  request. Without one it is refused with `invalid`, saying so, and nothing is
  written.
- `archive` is finished: the task is given `completed: <today>` unless the
  request or the note already says a day (an empty `completed` says none), and
  moving it out of `archive` takes `completed` away.
- A status is read as the index reads it: `"waiting "` or `["waiting"]` is
  Waiting, and is written back as `waiting`. A `waiting_on` of only blank
  names is nobody.

Moving a vault's tasks from older statuses to these eight is done in the app,
from the Inbox, never through the API: it rewrites every task, the Task type
and the views and automations that name a status, previewed first and undone
as one run.

### Timeblocks (P31-01)

A block is a note of type `block` (ADR-0030): `start` and `end`, each a day
and a time (`2026-10-12T09:00`), `tasks`, links to the tasks it holds, and
`gcal_event_id` and `gcal_etag` for the Google event it will sync with. Blocks
are made, read and changed through the notes routes like any other note. The
app writes the Block type into a vault once its tasks follow GTD; the API
never writes `.atlas/types`.

`POST /v1/query` with `"schedule": true`, on a query of `task`, adds a last
column, `schedule`, to each row: the task's
`{ estimate, scheduled, done, overBy }`, in minutes, as the task's page shows
them.

- **scheduled** sums the blocks linking the task. A block holding one task
  gives it all of its time; a block holding several shares its time by what
  each has left of its estimate — in proportion when they need the whole
  block, else each what it has left, and the rest in equal parts to the tasks
  with no estimate. Shares are whole minutes that add up to the block. Blocks
  that overlap each count, so the task reads as over-scheduled.
- A block's length is its wall-clock length as written, across midnight
  included; one without a time at both ends, or ending no later than it
  starts, gives nothing.
- **estimate** is null when the task has none; `2h` and `1h30m` are read as
  well as minutes, a day or a week is not. **done** is all of the estimate
  once the task holds the status ticking writes (`archive`), else 0, and null
  with no estimate. **overBy** is how far scheduled runs past the estimate.
- `schedule` on another type, or beside a `schedule` column, is `invalid`. A
  schedule the index could not read whole is `query_failed`, never a short
  answer.

### The Archive

Archiving is the app's Archive command, for up to 100 notes at once — and the
one move the API makes (ADR-0016). Each note moves under `Archive/` at the path
it had — `Projects/X.md` becomes `Archive/Projects/X.md`, numbered if that is
taken — and gets `archived: <today>` and `archivedFrom: <where it was>` in its
frontmatter; the rest of the file is kept byte for byte. If the note already
had keys of those names (or `archivedPrior`), their text is kept under
`archivedPrior` and given back exactly as it was written. A note too many
folders deep for Atlas to read it once it is under `Archive/` is refused.

`POST /v1/unarchive` puts each note back at its path without `Archive/` —
`Archive/Projects/X.md` goes to `Projects/X.md` — numbered if something has
taken it since, and takes the stamp off. `archivedFrom` is only used to spell
that same place as the note had it (another case, or without the number
archiving gave a clashing name): editing it, through `PATCH .../properties` or
anything else, never sends a note to another folder, another name or another
extension. Moves happen only in user space and never overwrite anything, and
`moves` names each folder as the vault spells it.

**The API never saves someone's typing.** A note open in Atlas with unsaved
typing is not moved, and a note linking to one that moved that has unsaved
typing is not rewritten: each is listed in `failed` with
`code: "unsaved_in_app"`. A pane holding a note that moved follows it to where
it went. Links in other notes that would stop opening a moved note are
rewritten once the batch has moved, and `linksUpdated` counts them.

A batch never fails as a whole for one note. `failed` lists each path that did
not move, with a `reason` for people: a path in `.atlas` or a hidden folder
(`node_modules` in any case among them), a file that is not a `.md` note, a
note that is already archived (or, to unarchive, is not), and a path with no
note. A note that moved but whose frontmatter could not be updated — its YAML
cannot be read, say — is listed under where it went, and so is each linking
note whose links could not be rewritten. A path finds its note whatever its
case. A vault switched mid-batch still answers what moved before the switch.

`GET /v1/archive` lists archived notes, most recently archived first, as
`{ path, title, from, archivedOn }` — `from` is where unarchiving puts it back,
and `archivedOn` is `YYYY-MM-DD`, or null for a note filed there by hand.
`search` keeps notes whose title or path holds every word, of its first 16. An
index that cannot run the listing is `query_failed`. `limit` is 1 to 500
(default 50); `next` is the `offset` for the next page, or null.

Search, saved views and queries leave archived notes out, as the app does,
unless `includeArchived` is true — `?includeArchived=true` on search, where each
archived hit then carries `archived: true`, and `{ "includeArchived": true }`
in the body of a run or a query. A dashboard's widgets and a calendar never
list them.

A view saved as an Atlas query (`query:`, ADR-0019) runs its query as the app
does: checked against the vault's types, its links resolved against the
vault's notes. Its text says whether archived notes are listed
(`INCLUDE ARCHIVED`), so `includeArchived` does not apply to it. A query that
does not read, or names something the vault lacks, is `invalid`, with the
problem as the app shows it. A dashboard's query widgets run the same way.

### The Inbox

Everything captured waits in the `Inbox` folder at the root of the vault —
tasks from `/v1/capture` and the app's capture, meetings imported into
`Inbox/Meetings/` — until it is processed (P30-01). `GET /v1/notes?folder=Inbox`
lists everything waiting there, `Inbox/Meetings/` included.

`POST /v1/inbox/process` is the Inbox's **Process**, for up to 100 notes at
once: each is filed under `project` — moved into the project's folder and
given `project: "[[…]]"` linking it. The project's folder is a folder named as
the project, beside its note (`Projects/Atlas.md` files into
`Projects/Atlas/`), or the folder a project is already the note of
(`Projects/Atlas/Atlas.md`). Only the note's name goes: `Inbox/Meetings/X.md`
lands as `Projects/Atlas/X.md`, numbered if that is taken. The rest of the
file is kept byte for byte; a `project:` the note had is replaced.

`project` is the path of a project or an area — a note whose `type:` is
`project` or `area` — that is still in use: not waiting in the Inbox itself,
not archived, not in `.atlas`, and not so deep that what is filed under it
would be past where the vault is read — nor one whose folder would be the
Inbox, the Archive or a hidden folder (a project at `Archive.md` would file
into `Archive/`). Anything else refuses the whole
request with `invalid` before a note moves, as does a path with no note.

Each note follows the Archive's terms below: it must be a `.md` note in the
Inbox (one elsewhere is listed in `failed`, and the rest carry on); it never
lands over anything; a note open in Atlas with unsaved typing is left where it
is with `code: "unsaved_in_app"`; links that would stop opening a moved note
are rewritten and counted in `linksUpdated`.

### Artifacts

`POST /v1/artifacts` saves a Claude artifact in one call: a note of type
`artifact` in `artifacts/` (made if the vault has none), named by `title` and
numbered if taken, and — when `html` is given — the page as `index.html` in a
folder beside it, `artifacts/<slug>/`, recorded on the note as `saved`. `kind`
is one of `page`, `deck`, `design`, `doc`, `other`, guessed from the page, then
the link, when left out. `url` must be `http` or `https`. `project` is the
project note's name.

**The 1 MiB body cap applies to the whole request.** A page larger than that,
and any other file the page uses, goes in chunks with
`PUT /v1/artifacts/{path}/files/{name}`, where `{path}` is the artifact note's
path and `{name}` the file's path inside its folder (`app.css`,
`img%2Flogo.png`), both encoded as one segment. Each chunk is `text` (written as
UTF-8) or `base64`; send ≤ 512 KiB of bytes per chunk. The first chunk has
`offset` 0 (the default) and creates the file — `exists` if it is already
there; each next one sends `offset` = the `size` the last answer gave, and is
refused with `conflict` if the file is not that long, so a retried or reordered
chunk never corrupts it. The first file makes the copy's folder and sets
`saved` and `saved_at` on the note. Only `html`, `htm`, `css`, `js`, `json`,
`svg`, `png`, `jpg`, `jpeg`, `webp` and `woff2` files, at most four folders
deep, 32 MB each, never hidden, never outside the artifact's folder, and never
`atlas-thumbnail.png` at its top, which is kept for the thumbnail.

Once the last file is in, `POST /v1/artifacts/{path}/thumbnail` pictures the
page's first screen (1280 × 800, as a 640 × 400 PNG) in a webview of its own
with no way back to Atlas, keeps it as `atlas-thumbnail.png` in the copy, and
sets the note's `cover` to it — unless the cover was set by hand to something
else, which is left alone. It answers with the note; `thumbnail_failed` (422)
says why when the page could not be pictured (only macOS can; a page that
never loads). The MCP tool `atlas_save_artifact` does all of this for you.

### Types, and the Thumbnail property

A relation's `target` is the type it points at, and `targets` every type it
may point at — `["project", "area"]` for a task's `project`, whose type file
says `target: [project, area]`; one type is `targets: ["project"]`, and a
property that names none `[]`. `target` is `targets`' first, kept for callers that read one.
`PATCH .../properties` refuses with `invalid` a relation set to link a note of
a type it does not point at — a person in a task's `project` — naming what it
takes. Only a link to a note that is there and says its `type:` is judged: a
link to a note not written yet, or one with no type, is written as it is.

`GET /v1/types` reports each property's `kind` as the type editor has it,
`thumbnail` included (U-15). A thumbnail's value is what the app writes: empty
or `auto` means Atlas pictures the note's own page, `false` means cleared, and
a path is a picture chosen. Set it with `PATCH .../properties` like any other
value. The generated picture itself is derived and lives in Atlas's cache,
never in the vault, so no route reads or makes it; an artifact's picture is the
exception, since it is kept in its saved copy (`/v1/artifacts/{path}/thumbnail`).

### A type's views

A type owns the views whose `type:` names it, and its page shows them as tabs
(issue atlas-archive#11, ADR-0023). `GET /v1/types/{name}/views` answers those tabs as the
app draws them: `{ type, views: [{ path, title, layout, order, virtual }],
total, next }`, in tab order — views placed by their `order:` first, by that number, then the
views nobody placed, boards before tables before lists and so on, then by
name. `title` is the tab's name (the view's `title:`, else its file name), and
`order` is the view's `order:` or null when it was never placed. `{name}` is
the type's `name` exactly as `/v1/types` gives it, one percent-encoded segment;
any other is `not_found`. A view of any layout is listed, wherever it is kept —
`.atlas/views` or a note elsewhere that says `atlas: view`.

It answers a page at a time: `limit` views (1 to 500, 100 when not given) from
`offset` (0 when not given), with `total`, how many the type has, and `next`,
the `offset` of the next page or null on the last. It pages by position, as
`/v1/archive` does, not by a path cursor as `/v1/notes` does: tab order is not
path order, so a path could not say where a page ends.

A type with no views answers one tab with `virtual: true`: the default table
its page shows, named and pathed as the app would write it the moment its tabs
change ("Task table", numbered past a name already taken). The app, its tabs
and this route name it by one rule: every file already in `.atlas/views` is
taken — a view, one lifted to Today or Inbox, or a note that is no view at all
— and so is every view kept anywhere else, compared in any case and either
Unicode normalisation, as the Mac's disk compares names. It is not a file, so
`/v1/views/{path}/run` cannot run it; its rows are `/v1/query` with the type,
or `/v1/atlas-query` with `FROM <type>`. Asking writes nothing — not even the
default.

A view's `order:` counts only as a number, or as text written as a plain
decimal (`2`, `-1`, `1.5`); `"0x10"` or `"1e3"` is no order, and the view
reads among the unplaced.

`GET /v1/views` names each view's `order` too, null for a dashboard. It lists
Today and Inbox first, when the vault has them, as the sidebar lifts them —
they are views, run by their paths like any other — then the other views
alphabetically, as the Views section reads, then the dashboards.

Adding, renaming, copying, moving and deleting a type's views stay in the app;
see "Not in the API, and why" below.

### Templates

A template is what a new note starts as — its properties and its text — and it
lives in `.atlas/templates`, never among the vault's notes (issue atlas-archive#16,
ADR-0026). The API reads them; it never writes one.

`GET /v1/templates` answers every template, as the Templates page lists them:
`{ templates: [{ name, path, uses }], typesWithoutTemplate }`. Every markdown
file under the folder is one — `.md` or `.markdown`, in a subfolder too, but
not in a hidden one such as `.git` or `node_modules`. They
come sorted by name as a lookup compares it (trimmed, in any case); of two with
one name, the one nearer the top of the folder comes first.
`name` is the file name without its extension; `path` is the file. `uses` is
what makes notes from it, empty when only the New menu offers it:

| `kind`     | Made from it                      | Matched by                                   |
| ---------- | --------------------------------- | -------------------------------------------- |
| `type`     | New notes of `type` (`label`)     | the type's label, then its name, in any case |
| `daily`    | Today's note (`POST /v1/daily`)   | the name `Daily`                             |
| `capture`  | Captured tasks (`/v1/capture`)    | the name `Task`                              |
| `artifact` | Saved artifacts (`/v1/artifacts`) | the name `Artifact`                          |

`typesWithoutTemplate` names the types no template serves: a note of one made
by the add button or `/v1/quick-add` starts with only its `type:` and the
values given.

`GET /v1/templates/{name}` answers one: `{ template: { name, path, uses,
properties, body } }`, `properties` its frontmatter parsed and `body` the rest,
byte for byte — what a note made from it starts with. `{name}` is one
percent-encoded segment, matched trimmed, in any case and either Unicode
normalisation, as `POST /v1/notes { template }` matches it; of two templates
with one name it answers the one that route would use. A name no template has
is `not_found`. A template path is not a note path: `/v1/notes/{path}` refuses
`.atlas/templates/…` as it refuses all of `.atlas`.

No route that lists or follows notes hands out a template: not `/v1/notes`,
search, backlinks, tags, queries or views, even when the index still holds a
link to one. Making, renaming, editing, moving to notes and deleting templates
stay in the app; see "Not in the API, and why" below.

### Images in notes

`PUT /v1/notes/{path}/images/{name}` saves an image for a note as a paste or a
drop does (U-12): in the folder **Settings → Images** chooses when the request
arrives — `attachments/` at the root (made when missing) or beside the note —
under `{name}`, numbered past any file there in any case (`chart 2.png`), and
never over one. It takes PNG, JPEG, GIF, WebP, SVG and HEIC, up to 20 MB, as
`text` or `base64`. Its bytes must be the kind its name says (a PNG's
signature, `GIF8`, `RIFF…WEBP`, an `ftyp` HEIF brand) — the app has the webview
draw an image before saving it, and a request has nothing to draw, so a HEIC
this Mac cannot show is saved rather than refused. An SVG's root element must
be `<svg`, and one holding an HTML doctype, `<html`, `<script` or an `on…=`
handler anywhere is refused.

An image of ≤ 512 KiB is sent whole, in one request (`offset` 0, `last` left
out or `true`), and saved at once. A larger one is an **upload** (A20-02),
staged outside the notes until it is whole, so nothing in the vault is ever
appended to:

1. The first chunk: `offset` 0, `last: false`. It must start as its kind does.
   The answer is `202 { upload: { id, size } }`.
2. Each next chunk: `offset` = the `size` the last answer gave, `upload` = the
   id, `last: false` — answered `200 { upload: { id, size } }`. A chunk past
   offset 0 with no `upload` is `invalid`; an unknown id is `not_found`; the
   wrong offset is `conflict`, and nothing is written.
3. The last chunk says `last: true`. The whole image is checked and moved into
   place under a free name, answering `201 { image }`.

The name in the URL of the last chunk is the one the image is saved under. An
upload given up on is left in the cache (`.atlas-cache/uploads`), never in the
notes. The answer is

```json
{
  "image": {
    "path": "attachments/Q3 chart.png",
    "size": 48213,
    "src": "../attachments/Q3%20chart.png",
    "alt": "Q3 chart",
    "markdown": "![Q3 chart](../attachments/Q3%20chart.png)"
  }
}
```

The note is not changed: write `markdown` into it with `append` or `body`, as
`atlas_add_image` does. `![[image.png]]` embeds and resizing are not written by
the app either.

### Atlas queries

`POST /v1/atlas-query` runs an Atlas query (ADR-0019) — the text the query
builder writes — read-only, checked against the vault's types and with its
`[[links]]` resolved against its notes, exactly as the app runs it:

```json
{
  "query": "FROM task, project WHERE status != done AND tag = #q3 SORT BY due GROUP BY project THEN status",
  "limit": 200
}
```

- **Rows** are `{ columns, rows, truncated, sql }`, the columns starting
  `path`, `title`, `type`. Every value in the query is a bound parameter; `sql`
  is the statement that ran.
- **Groups.** With `GROUP BY`, `groups` lists the groups a list or table shows:
  `{ label, value, rows, groups }`, where `rows` are indexes into `rows`,
  `value` is null for the rows with none, and `groups` are the sub-groups of
  `GROUP BY a THEN b` (empty at the last level). A select's groups come in the
  type's order, a relation's are named for the note it points at, and a group
  no row is in is left out. Without `GROUP BY` there is no `groups`.
- **Archived notes** are left out unless the query says `INCLUDE ARCHIVED`; the
  body's `includeArchived` is refused, so the answer never depends on two
  places saying different things. Notes in `.atlas` or a hidden folder are
  never listed, never read through a relation (`project.owner` shows, sorts
  and matches nothing of one), and never name a group: a relation to one
  reads as its link.
- **Limits.** `limit` is 1 to 5000; the query's own `LIMIT` wins when it is
  smaller, and with neither, 500 rows come back. `truncated` says more
  matched. A query holds 2000 conditions at most, and its text 200,000
  characters.
- **Mistakes in the text** are `invalid`, with where they are:

```json
{
  "error": {
    "code": "invalid",
    "message": "Line 2, column 7: A task has no field called stauts.",
    "at": { "line": 2, "column": 7, "start": 16, "end": 22 }
  }
}
```

`line` and `column` count from 1, columns in characters; `start` and `end` are
the offsets of the characters at fault. The index refusing the statement is
`query_failed`, with no path on this machine in its message. A query view run
through `/v1/views/{path}/run` is refused the same way, and answers up to its
own `LIMIT`, with `truncated` saying when that cut it short. A dashboard's
failed widget carries its message the same way, without paths.

### Groups, boards and "+ New"

`GET /v1/views` names each view's `groupBy` — a board's columns, a table's or
a gallery's groups — and `subGroupBy` — a board's swimlanes, a table's
sub-groups — or null for none (issue atlas-archive#6). A `subGroupBy` equal to the
`groupBy` splits nothing, so it reads as null, as the app draws it.

Running a saved view whose layout draws groups (a table, a board, a gallery)
answers its `groups` beside its rows, shaped as an Atlas query's are (below):
`{ label, value, rows, groups }`, `rows` being indexes into `rows`, and
`groups` the sub-groups — a board's swimlanes inside each column. A gallery
draws only its first level. The groups come in the order the app draws them: a
select's in the type's order (reversed when the view sorts by it descending),
a relation's named for the note, "No value" last. A board lists every column,
an empty one too — a select's every option and, for a relation, every note it
can point at (not archived notes or templates) — since an empty column is
somewhere to move a card to; inside a column, only the lanes a card is in are
listed. What a view groups by is read for its rows even when the view does
not show it as a column; `columns` is the view's own either way. A grouping by
a field that holds several values groups nothing, as in the app. A list, feed,
calendar or timeline, and a view grouping by nothing, answers no `groups`.

`POST /v1/views/{path}/move` moves a card on a board as a drag does: `note`
is its path, `group` the column and `subGroup` the lane it goes to — each a
group's `value` as a run answers it, null for "No value" — one or both. A
group must be one the board draws: a select's declared option, a note a
relation can point at, a value a card on the board already has, or null; it is
matched as the board matches its columns — trimmed, `[[atlas]]` for
`[[Projects/Atlas]]` (a relation by its first link's note name), an unticked
or missing box alike — and written as the board spells it, typed by its
property's kind (a number as a number, a checkbox as `true` or `false`). Any
other group is `invalid`, naming the board's groups, so `Done` for `done` is
refused rather than writing a column the type does not have. It is one
property write (see Writing safely: through the pane holding the note), and
the app's own rule decides whether it finishes the task: a type with a status
is finished by its done option, whether that is the board's columns or its
lanes; a type without one by its column's `done`, else its last option.
Finishing a repeating task rolls it forward to its next date once, keeping the
other group it was dropped into.

**A move that finishes the task needs `ifModified`** — the note's `modified` as
the caller read it — and is `invalid` without one. A repeating task is back in
its first status once finished, so the same move sent again would finish it,
and move its date on, a second time; with `ifModified`, the retry is refused
as `conflict` because the first move changed the note. Any other move takes
`ifModified` as optional. A group the card is already in is not written, so
`moved` is false and nothing is written when the card is in both already.
Only a board's cards move: any other layout, a lane on a board with none, a
query or SQL view, a note of another type than the view lists, a view or a
dashboard (whose `type:` names what it lists), or no `group` and no `subGroup`
is `invalid`; set a note's properties with `PATCH .../properties` instead. A
dashboard as the board is `not_found`.

`POST /v1/views/{path}/notes` adds a note as "+ New" inside a group does: of
the view's type, given `group`'s value (and `subGroup`'s, a board's lane or a
table's sub-group) typed by its property's kind — a number as a number, a
checkbox's `true` as ticked — while "No value" and the unticked group give it
nothing. It is made at the vault's root, named `name` or `New <type>`, numbered
past any note of that name rather than refused, as the app does — several added
at once each get their own number. A `name` that would not make a `.md` note
the API can read back (`Plan.markdown`) is `invalid`, as `POST /v1/notes`
refuses it; a name with no free number left after many tries, because notes
kept taking them, is `conflict`, and retrying is safe. With neither,
it is a plain note of the type. A `group` in a view that draws no groups, or a
`subGroup` in one with no second level, is `invalid`; so is a query or SQL view.

Changing a view's `groupBy` or `subGroupBy` is not a route; see Not in the API.

### Calendars

`POST /v1/views/{path}/calendar` shows a saved view's notes as its calendar
does (U-14). `range` is `month`, `week`, `3day`, `day` or `agenda` — the view's
own `calendarRange` when omitted — and `anchor` a day in it, `YYYY-MM-DD`, today
when omitted. `days` lengthens an agenda (1–366, 30 by default) and is `invalid`
for any other range. `days` in the answer lists every day shown: a week starts
on Monday, a month is its six-week grid. Each event is
`{ path, title, start, end, allDay, on }`, `start`/`end` as the note writes them
(`2026-09-22` or `2026-09-22T14:30`, wall-clock, never converted), `end` from
the view's timeline end when its timeline starts on the calendar's date, and
`on` the days of the range it is on. Notes with no readable date are counted in
`unscheduled`. The view must name a `dateKey`; a SQL view or one with no date
is `invalid`, a dashboard `not_found`.

### Quick add

`GET /v1/quick-add` lists the types the floating add button offers (U-13), as
**Settings** lists them in the vault's `.atlas/settings.md` — Task when unset —
each `{ name, label, fields }`, `fields` being the property keys the button
asks for. `POST /v1/quick-add` adds a note as the button does: from the type's
template when there is one, `values` (text by key) written as each kind stores
them, in the folder the button uses (a task where capture puts one, anything
else at the root), numbered if the name is taken. Any type the vault defines is
accepted, as a type's table **New** accepts it; an unknown one is `not_found`.
Which types the button offers, and where it sits, are Settings, which the API
does not change.

### Profile

`GET /v1/profile` answers who uses the vault, as **Settings → Profile** keeps
it in `.atlas/settings.md` (ADR-0024): `{ profile: { name, preferredName,
placeholder } }`, each name `null` when unset. A caller that needs the person's
name — an owner, an author, an attendee — uses `name`; when it is `null`, it
writes `placeholder` (`[Your name]`) or asks, and never guesses one from a
username, an email address or a path. The route only reads: the name is
changed in Settings, and the API never writes `.atlas`. A settings note that
cannot be read is an error, not an empty profile.

### Sources

`POST /v1/sources/{path}/refresh` refreshes a source note now, as its
**Refresh** button does (P12-06), and answers
`{ report: { ran, from, records, created, replaced, updated, missing, unkeyed, truncated, error } }`.
The source note is found as a view is: in user space or under `.atlas`, where
sources usually live (`.atlas/sources/Issues.md`), read and never written. It is
refused as `invalid` unless its `into` folder is in user space and any vault
file it reads is too — a note anyone could have written must not copy a hidden
file such as `.git/config` into notes, nor write over `.atlas`. **A source that
sends a secret, or reads a SQLite file outside the vault, runs only from
`.atlas/sources`** (A20-02), which the API cannot write: anywhere else it is
`forbidden`, nothing is fetched, and the message says to move the note into
System → sources. A public feed runs from anywhere. A SQLite file outside the
vault opens only if it was picked on this Mac.
A feed that fails is a report whose `error` says why, not an error answer. A
source already being refreshed — by its pane's timer or another request — is
`conflict`, and so is one the API refreshed less than 30 seconds ago, with
`retryAfter` saying how long is left. The refresh is bound to the vault the request arrived for: only its
secrets are sent, each filled in by the host and only to the sites it was bound
to in Settings (ADR-0017), so a source note the API pointed elsewhere is
refused by the host. `from` is the URL as the note writes it, `{{secret:name}}`
and all; no route ever carries a secret's value, and none lists secrets.

### Tags

A tag is named in the URL as one segment, its `#` optional and its `/`s
encoded: `/v1/tags/para%2Fresource/notes`. It is found however it is cased,
as the vault counts it (`IDEA` is `#idea`), and answers name it as it was
first written. A name no tag can have — no letter, or a word opening or
closing with `_` (ADR-0018) — is `invalid`; a tag no note uses is `not_found`.

`GET /v1/tags` is the tags page's tree: each tag `{ name, label, count, total,
children }`, `count` its own uses and `total` those of everything nested under
it, sorted by name or, with `?sort=frequency`, by `total`. Tags are counted in
the notes the API reads — as `/v1/notes` lists them, and as a rename writes
them — so a tag used only in `.atlas` templates or a hidden folder is not in
the tree, and is `not_found` to the other tag routes. Archived notes are left
out of the tree and of a tag's notes, as the tags page leaves them out; a
rename still rewrites them, so a note unarchived later does not keep the old
name, and a tag only archived notes use is one a rename would merge into.

`GET /v1/tags/{tag}/notes` pages the notes using the tag or one nested under it,
`{ path, title, uses }` in path order, continued with `cursor` as `/v1/notes`
is. Notes in `.atlas` are left out.

`POST /v1/tags/{tag}/rename` renames the tag, and every tag nested under it,
in the `tags` property and the body of each note, as the tags page does
(Phase 20). It answers `{ rename: { from, to, files, uses, mergesInto, notes,
skipped } }`; with `dryRun: true` that is all, and nothing is written. Otherwise
it also renames, answering `{ report: { updated, failed } }`. Each note is read
again and written against the version it read, byte for byte apart from its
tags, so a note changed in between is `failed`, not overwritten. A note open in
Atlas with unsaved typing is left alone and `failed` — the API never saves
someone's typing for them — and a pane holding a note with nothing unsaved is
reloaded. Notes in `.atlas` or a hidden folder (a template's `tags:`) are never
written: they are listed in `skipped`. A new name no tag can have, or one
nested under the tag itself (`idea` to `idea/sub`), is `invalid` with the
reason. So is a name whose last word is one letter (`plan a`): its closing
`#` reads as `C#` does, so `#plan a#` would read back as `#plan` (ADR-0018). A
note where the new name, written with its closing `#`, would run into what
follows it (`#idea_`, `#idea#x` renamed to `my tag`) keeps the old name and is
listed in `skipped` with why. **A rename into a tag already in use merges the
two** — and a tag used only as the parent of others (`#beta` when `#beta/y` is
written) is in use — and renaming back cannot part them again, so it is
`exists` unless the request says `merge: true`; `mergesInto` in the preview
names that tag. Renames in a vault run one at a time, the app's tags page's
included, and whether one merges is asked again just before it writes: two
renames into one new name, sent together, are one rename and one `exists`.

**A rename that timed out may still finish.** The API writes note by note and
does not stop when the caller gives up waiting. Preview again with `dryRun: true`
before retrying: it shows what is left to rename, and whether the new name is
now in use.

A cursor is only good for the route that handed it out: one that does not
decode to a note the API reads is `invalid`, never an empty last page.

### Automations

Automations (Phase 25) are read here and run in the app. The three routes
read the rules in `.atlas/automations` and their logs, as the Automations page
does, and write nothing.

`GET /v1/automations` lists every rule, by name: `{ id, name, path, enabled,
when, which, olderThanDays, do, set, schedule, action, lastRun, nextRun,
paused }`. `when`, `which`, `olderThanDays`, `do` and `set` are the rule as its
file writes them (`set` is null for an archiving rule); `schedule` and `action`
say the same in the app's words. `lastRun` is the newest run, `{ at, kind,
trigger, summary }` — `kind` is `failed` when its query did not read — or null.
`nextRun` is when it next runs by itself, as the app's clock counts it, a local
time `YYYY-MM-DDTHH:MM:SS`; null when it is off, runs only on opening or by
hand, or is paused until run by hand. `paused` says why the app's clock is
holding a rule back — its log could not be written, or it keeps failing — and
is null otherwise. A file that says `atlas: automation` and cannot be read as a
rule is listed apart, under `broken`, as `{ path, name, problem }`; it never
runs.

`GET /v1/automations/{id}/log` answers a rule's log, newest first, up to
`limit` entries: each `{ kind, at, heading, summary, done, left }`, with
`trigger` and `capped` on a run, `trigger` and `problem` on a run that could not
start, and `of` on an undo. `done` lists what it did to each note — `{ kind:
"archived", from, to }`, or `{ kind: "set", path, key, before, after }`, a value
being `{ value }` or `{ absent: true }` — and `left` the notes it matched and
left alone, with why. `truncated` says older entries were left out. A
`problem`, a reason in `left`, a `summary` and `paused` never carry this
machine's paths: each is answered with `<path>` in their place, even from a log
written before the app stopped writing them.

`POST /v1/automations/{id}/dry-run` answers what the rule would do if it ran
now, found by the same use-case the app's Dry run and every run use: `{ plan:
{ do, set, summary, notes, passedOver, passedOverMore, capped, cap } }`.
`notes` are the notes it would act on, at most `cap` (500, the most one run
does), and `capped` says more matched. `passedOver` lists at most 500 of the
notes it matched and would leave alone, with why; `passedOverMore` counts the
rest. A set rule leaves out notes that already hold its values. It
reads the notes and the index and writes nothing — no note, no log entry. A
rule that is turned off can be dry-run too.

`{id}` is the rule's `id` as the list gives it, encoded as one segment, found
whatever its case or Unicode normalization, as the disk finds its log. Two
rules whose ids differ only so share one log file, so the second (by file
name) is listed under `broken`. An id no rule has is `not_found`, repeating
at most its first 80 characters. A broken rule, named by
its name or its file's, is `invalid` with why it cannot be read — it has no
log to trust and nothing to plan. A rule whose query does not read, or that
the index cannot run, is `query_failed`, with why and without this machine's
paths. A vault switched while a route reads is `no_vault`.

### Not in the API, and why

- **Secrets.** Neither values nor names: ADR-0017 keeps them in the host and
  Settings; a source names one, and the host decides where it may go.
- **Types, views, dashboards, SQL queries and settings as definitions.** They
  live in `.atlas/`, which the API reads (`/v1/types`, `/v1/views`, running a
  view) but never writes: a caller that could would change what every type,
  view and template means (see Paths). The type editor, saved-view editing
  (P17-02..04) — its grouping (`groupBy`, `subGroupBy`) included — dashboard
  editing, Settings → Images and the add button's list stay in the app; a
  view's grouping is read with `/v1/views`. Tick-to-done and property edits
  are ordinary property writes, which the API has; a board drag is
  `/v1/views/{path}/move`, which writes the card, never the view.
- **Adding, renaming, copying, moving and deleting a type's views** (issue
  atlas-archive#11). Each writes a view in `.atlas/views` — a new file, its `title:`, a
  byte-for-byte copy, its `order:`, or the file to the Trash — and the first
  change to a type with no views writes its default table too. The API reads
  the tabs (`/v1/types/{name}/views`) but never writes `.atlas` (ADR-0016's
  addendum for issue atlas-archive#11 says why, and what an exception would take).
- **Making, renaming, editing, deleting and moving templates to notes**
  (issue atlas-archive#16). A template is a file in `.atlas/templates`, and its name is
  what ties it to the notes made from it: a caller that could write one could
  change what every new Person, today's note or every captured task starts
  as, and a rename or a delete silently stops a type using it. The API reads
  them (`/v1/templates`, `/v1/templates/{name}`) and makes notes from them
  (`POST /v1/notes { template }`), but never writes `.atlas` — ADR-0016's
  addendum for issue atlas-archive#16 says why, and what an exception would take.
- **Saving an Atlas query as a view.** `/v1/atlas-query` runs any query, but
  a query view is a note in `.atlas/views`, and the API never writes `.atlas`
  (ADR-0016): a caller that could save one could also rewrite the views James
  keeps in his sidebar and on his dashboards. Saving, renaming and editing a
  query view stays in the query builder; its saved text can be read with
  `/v1/views` and `/v1/notes/{path}`, and run with `/v1/views/{path}/run`.
- **Running, undoing, and making or editing an automation.** A rule and its
  log are notes in `.atlas/automations`, which the API never writes
  (ADR-0016): a caller that could make or edit one could set a rule that
  archives or rewrites the vault on a schedule, long after the call. A run —
  and an undo — moves or rewrites up to 500 notes at once, and the app runs
  them one at a time, with a log entry for each and its undo ready; a run from
  outside would do all that with no one watching the page it reports to. So
  running a rule now, undoing its last run, turning one on or off, and making,
  editing or deleting one stay on the Automations page. The API reads them —
  the list, each log, and a dry run that writes nothing — and a note a rule
  would archive can still be archived with `POST /v1/archive`.
- **Move, rename, delete, and making folders.** ADR-0016: every v1 write is
  additive or guarded. (Renaming a _tag_ is a guarded write to notes' text,
  not a rename of a file; see Tags.) The moves the API makes are archiving
  and unarchiving, and processing the Inbox (ADR-0016's amendments): in user
  space only, never over anything, to a place fixed by the note's own path —
  and, for the Inbox, by the project it is filed under — at most 100 notes,
  and never saving typing — see the Archive and the Inbox above.
  Moving or deleting notes, views and dashboards (P17-01)
  stays in the app; `POST /v1/notes` needs its folder to exist, so a mistyped
  folder never scatters notes.
- **Setting a vault's types up for PARA** (P30-01). Opening a vault that has a
  Project type writes the Area and Resource types it lacks; anything more —
  PARA's types for a vault without one, or `project` added to its own Task and
  Meeting types — the Inbox offers, and writes only when James accepts. Each is
  a write into `.atlas/types`, which the API never makes (see Paths): the
  types it would write can be read with `/v1/types` once they are there.
- **Writing the Block type** (P31-01). The app writes it once a vault's tasks
  follow GTD; it is a write into `.atlas/types`, which the API never makes.
  Blocks themselves are notes, made and changed through the notes routes.
- **Picking a SQLite file for a source.** A file outside the vault opens only
  once it was picked on this Mac in the system dialog; a request cannot pick one.
- **Page pictures.** Derived, in the cache; see Types above.

Filter operators: `is`, `isNot`, `contains`, `startsWith`, `greaterThan`,
`lessThan`, `isEmpty`, `isNotEmpty`.

## MCP

`apps/mcp` exposes each route as a tool (`atlas_search`, `atlas_read_note`,
`atlas_create_note`, …; `atlas_save_artifact` covers the three artifact routes,
chunking what does not fit, and `atlas_add_image` sends an image whole or as
an upload, then appends it to the note; a `file` it reads only from the image
folders its README names) over stdio and reads the connection file itself.
`atlas_calendar`, `atlas_quick_add_types`, `atlas_quick_add` and
`atlas_refresh_source` are the calendar, quick-add and source routes;
`atlas_profile` is the profile route, read-only;
`atlas_list_templates` and `atlas_read_template` are the template routes, read-only;
`atlas_tags`, `atlas_tagged_notes` and `atlas_rename_tag` are the tag routes;
`atlas_rename_tag` previews unless called with `dryRun: false`.
`atlas_archive`, `atlas_unarchive` and `atlas_archived` are the Archive's;
`atlas_process_inbox_item` is the Inbox's Process, filing one note under a
project or an area; and
`atlas_search`, `atlas_run_view` and `atlas_query` take `includeArchived`, and
`atlas_query` takes `schedule` for a query of tasks.
`atlas_run_query` runs an Atlas query (`/v1/atlas-query`); it has no
`includeArchived`, since the query's own `INCLUDE ARCHIVED` says it.
`atlas_automations`, `atlas_automation_log` and `atlas_automation_dry_run` are
the automations routes, all read-only. `atlas_move_card` and `atlas_add_to_view`
are the board move and the "+ New" in a group; `atlas_move_card` is not marked
idempotent, since a move into done sent twice would finish a repeating task
