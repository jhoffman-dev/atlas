Found by the T-02 sweep; outside that card's substring-matching scope.

**`e2e/search.spec.ts:77`** clicks Rebuild and then checks `'3 notes indexed'` —
text that was already on screen before the click. It passes whether or not a
rebuild happened. It needs to observe the rebuild itself: the status passing
through its working state, or the index reflecting something that changed on
disk only a rebuild would pick up.

**`e2e/host.ts` `vault.write`** uses `writeFile`, which truncates before it
writes. An app read that lands in between sees an empty or partial file — the
same shape as the T-03 sources race, waiting for a test that writes while the
app reads. Write to a temporary file and rename it into place, which is what
the real Rust host does (`write_text` in `vault.rs`), so the stand-in cannot
produce a torn read the real host never would.

**Done (2026-09-26).** The Rebuild test writes `bread.md` behind the app's back
(the stand-in host watches nothing), then waits for `4 notes indexed` and a search
hit on a word only that note has — neither can appear without a rebuild. Proved:
with `onRebuild` a no-op it goes red on `4 notes indexed`. `vault.write` writes a
`.e2e-tmp` file beside the target and renames it over, as `write_text` does.
