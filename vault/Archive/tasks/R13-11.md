When a pane's last save is refused and the pane is closed, the work is now kept
and handed back the next time that note is opened, rather than being dropped
into an empty catch. But the store is in memory.

That covers what actually strands work — closing a pane, switching notes — and
not what does not: quitting the app. The gap is honest rather than hidden, and
it is stated where it is implemented, but somebody will eventually lose
something to it.

The fix is the same shape as the other per-viewer state: a store behind a port,
with the adapter writing somewhere durable. Not the vault — this is unsaved
work that the vault by definition does not have — so a UI-state file, and a
decision about when it is cleared.

## Done

- **Where:** `localStorage`, behind the `StrandedEditStore` port
  (`apps/desktop/src/notes/browser-stranded-store.ts`), one entry per note
  under `atlas.stranded:"<vault>":<path>`. A document is roughly twice its
  markdown as JSON (PLAN.md: 18 KB → 37 KB), so the quota is a few-megabyte
  note away. A refused write keeps the work in memory and the notice says it
  will be lost if Atlas quits.
- **Cleared:** when the note is opened again and the work handed back; when it
  is discarded from the notice (for a note that was deleted); after 30 days
  (`STRANDED_EDIT_LIFETIME_MS`), checked on load; and an entry that does not
  parse is removed as it is read.
- **Changed underneath:** the file's modification time is read when the work
  is kept. If it differs when the work is handed back, the pane shows the
  work with the refused-save alert and its Overwrite / Discard buttons, and
  writes nothing — autosave included — until one is chosen. Closing it
  undecided keeps it again against the same time.
