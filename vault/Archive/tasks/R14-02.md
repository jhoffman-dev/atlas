`NotePane` is keyed by path, so opening `notes.md` in vault B after vault A had `notes.md` open does **not** remount the editor. Whether the editor then shows B's text depends on it adopting a new document without a remount.

That is the same shape as a bug already found once (R13, found by the cross-pane fixer): tiptap reads `content` only at creation, so a pane kept A's text on screen while adopting B's modification time — and the next keystroke saved A's body over B's file, and the save was accepted. `note-editor.tsx` now adopts a re-read by identity check, which may cover this; nobody has checked.

Write the e2e first: two vaults with `notes.md` of different text and the same mtime, open A's, switch to B, open B's, assert the editor shows B's text, type, save, and assert B's file holds B's text plus the typing and none of A's. If it is already right, the test is the deliverable. If the key should include the vault, that is the fix.

**Finding:** already right, twice over. A different vault makes `noteKey` differ, so `useNote` blanks to "Reading…" and `NotePane` unmounts the editor; and were that lost, the identity-check adoption in `note-editor.tsx` would still put B's document on screen. Only with both broken does the editor show "Written in vault A." under B — which the carried-layout tests in `e2e/vault-switch.spec.ts` catch. The tests are the deliverable.
